## 【方法论】设计稿比对：像素取证比肉眼可靠得多（含一次自我推翻）

对设计稿做差距分析时，**不要凭缩略图目测下结论**。本次流程与教训：
1. `PIL` 裁切 + 放大（LANCZOS 2~3x 看整体结构；**NEAREST 6x 看形状**——LANCZOS 会把小色块洗掉）。
2. 先定位**行基线**再采样：设计稿 (1024x572) 的表头在 y≈106-111，**首数据行在 y≈129 起**。
   我第一次把 y=112..128 当成首行去采样，那里其实是表头与首行之间的空白，
   于是"众数是平坦背景"→ 我错误地得出「设计稿角色徽章没有底色」。
   6x NEAREST 放大后真相是：**有胶囊底色**，只是我采错了区域。**采样前必须先确认坐标落在目标上。**
3. 竖向分隔线用**列扫描**（逐列统计"高于本底亮度"的像素占比）判定，别靠"好像看到一条线"。
   实测：设计稿与当前实现在原文/译文之间**都没有**贯穿竖线。
4. 设计稿是低分辨率 JPEG，小字（10px）经 JPEG 模糊后峰值亮度远低于真实字色，
   **不要用峰值像素反推字号/字色**。尺寸类结论必须按窗口宽度比例换算（设计 1024 → 实现 1280，系数 1.25）。

## 模块 1 闭环：GARbro/工具链驱动的自动解包流

**编排决策（关键架构）**：解包**逐封包短 RPC**（`list_archives` → 每封包一条 `unpack_archive`），
而非单条长任务——长 RPC 会堵死 StdIO 分发器（后续请求全排队）且无法取消。拆开后：
取消粒度=封包（批间检查 CancellationToken，取消后停发后续）、进度=已处理/总数（真实进度）、
单封包失败跳过续走。**完整击杀远端子进程需 JSON-RPC cancel 通知扩展**，本切片以
「取消停发 + Python 侧 subprocess timeout 治理」达成无失控长任务（已如实汇报）。

**Python（core/archive/orchestration.py + 2 个 RPC）**：
- `_UNPACK_RECIPES` 按引擎注册封包 glob + 命令模板（arc_unpacker 风格草案，工具中立——
  接入真实 CLI 校准模板即可，编排零改动）；`list_archives` 排除 `.galpipeline` 自身；
- `unpack_archive`：产物落 `raw/scripts/{stem}/`，**幂等**（目录非空即 skip，不覆盖用户整理过的产物）；
  拒绝解包工作区内部文件；复用 ExternalCliExtractor（超时/退出码/空产出三重校验）；
- 工具路径由 C# 侧 Toolchain 解析后传入（本侧不做工具定位）。

**C# 宿主**：`ListArchivesAsync`/`UnpackArchiveAsync` IPC；VM `StartUnpackAsync`
（Resolve(GARbro) → Missing 抛 ToolchainMissingException 引导 / Corrupted 抛详情 →
逐封包循环 + UnpackProgress + JsonRpcException 跳过 → 完成后 RefreshProjectScripts 重扫
